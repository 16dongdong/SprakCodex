# 额度重置与预热

## 0.6.4 行为

- 账号列表的主额度条下直接显示重置倒计时，所有账号共享一个秒级时钟。
- 未提供重置时间显示“未提供”，时间到期显示“等待刷新”，不推算上游未返回的新周期。
- 服务运行时默认自动预热：每 5 秒检查持久化任务，单工作线程按到期顺序处理账号；多个账号同时到期会依次执行。
- 仅识别服务端明确提供的 300 分钟和 10080 分钟主额度周期，不按主次槽位猜测周期。
- 手动兑换重置成功后加入即时任务，不会自动兑换或消耗重置次数。
- 预热前刷新额度，调用现有账号预热流程，完成后再次刷新，读取上游真实重置时间。预热会产生实际模型请求和用量。
- 缺少重置时间且从未观察到过该周期的账号不凭空调度；禁用、失效账号不自动调用。

## 持久化与失败语义

`139_resetWarmup.sql` 为每个账号最多保留两条自然周期和一条手动重置任务。任务领取使用 SQLite IMMEDIATE 事务，同一账号同时到期的周期合并调用；账号删除后关联任务级联清除。

领取状态在网络调用前提交，重启不会重新调用已领取任务。调用失败或进程异常退出时不自动重发不确定请求，避免重复产生用量；查看预热请求日志或服务日志后可手动预热。上游是否立即开启新周期以刷新结果为准。

更新排空期间不领取新任务，已开始的预热纳入请求生命周期计数。

## 验证

`cargo test --offline --manifest-path backend/Cargo.toml -p codexmanager-core --test resetWarmup`

覆盖截止边界、重复快照、周期切换、缺失时间、停用账号、手动重置与自然到期合并。测试使用虚构时间和隔离数据库，不消耗真实账号的重置次数。
